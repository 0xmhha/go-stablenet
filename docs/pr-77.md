[StableNet] 거버넌스 GasTip 복원 제안 시 트랜잭션 Pending Pool 정체 이슈 원인 분석 및 수정

설명

## 배경
StableNet에서는 거버넌스를 통해 gasTip 값을 동적으로 변경할 수 있음.

기본값은 27600 Gwei이며, 거버넌스(GovValidator) 제안을 통해 변경 가능함.

거버넌스 GasTip 변경 이후, 빈 블록에서 currentBlock이 갱신되지 않는 문제 수정  

AnzeonTipEnv.SetCurrentBlock()가 state root 동일성만 체크하던 문제

변경된 minTip 조건을 만족할 수 없는 트랜잭션이 remote pool에 남는 문제를 완화/수정

## 현상
다음 시나리오에서 트랜잭션이 처리되지 않는 문제가 발생함:

## 재현 시나리오
초기 상태: gasTip = 27600 Gwei

거버넌스 제안 → 30000 Gwei로 변경 (정상 반영)

이후 27600 Gwei로 복원하기 위한 거버넌스 제안 트랜잭션 제출

## 결과
해당 트랜잭션이 pending pool에 지속적으로 남아 있음

블록에 포함되지 않으며 상태 변화 없음

동일 조건에서 반복 재현 가능

## Background
1. AnzeonTipEnv: currentBlock 갱신 지연 문제
원인

따라서 block N에서 실행된 거버넌스 변경은 block N+1 header의 GasTip 값에 반영됨


2. RemotesBelowTip: 잘못된 tip 비교 로직
원인

unauthorized account의 경우:

tx pool 검증 시 AnzeonTipEnv.GetAnzeonTipCap() 결과를 cache하며, unauthorized account는 block.GasTip()이 cache됨

## RemotesBelowTip: AnzeonTipCap 캐싱 설계

### 문제: 매 블록 조회 시 부하
`RemotesBelowTip`에서 AnzeonTipCap을 **매 블록마다 읽고 설정**하는 방식은 트랜잭션이 많을 경우 부하가 된다.

- `go-stablenet`의 blocktime은 **1초**로 매우 짧다.
- 따라서 블록 생성 주기마다 AnzeonTipCap을 조회·설정하는 비용이 누적되면, tx가 많은 상황에서 무시할 수 없는 오버헤드가 된다.

### 해결: 비인가 계정 GasTip 캐싱
비인가(unauthorized) 계정의 경우 **GasTip을 고정값으로 사용**하기 때문에, 값이 변동하지 않는 한 매번 다시 조회할 필요가 없다.

- 변동이 없다면 GasTip을 **캐싱하여 사용**하는 것이 속도(조회 횟수 감소)와 메모리 사용 측면에서 유리하다.
- 즉, AnzeonTipCap을 매 블록 조회하는 대신, 캐싱된 GasTip을 재사용하여 1초 blocktime에서의 반복 조회 부하를 제거한다.

### 캐시 무효화: 거버넌스 GasTip 변경 시
거버넌스를 통해 GasTip이 변경된 후에는, pool에 남아있는 tx들 중 **캐싱된 GasTip보다 낮은 값으로 설정된 tx는 버린다.**

- 거버넌스 변경으로 새 minTip 조건을 만족할 수 없게 된 tx가 pool에 정체되는 것을 방지한다.
- 이는 위 "RemotesBelowTip: 잘못된 tip 비교 로직" 및 pending pool 정체 이슈와 직접 연결된다.


## 통과 기준 유닛테스트 (수정 완료 시 반드시 통과)

### 대상 1.
- 신규 헤더의 state root가 기존과 같아도 GasTip 값이 다르면 currentBlock이 갱신되어야 한다.
- root·GasTip 모두 동일하면 갱신하지 않는다.
- gasTipChanged(a, b): 둘 다 nil→false, 한쪽만 nil→true, 값이 같으면(다른 포인터라도) false, 다르면 true.

### 대상 2.
- 트랜잭션의 캐시된 AnzeonTipCap을 기준으로 임계값과 비교한다. AnzeonTipCap < threshold면, tx.GasTipCap()이 임계값 이상이라도 드롭 대상에 포함되어야 한다.
- AnzeonTipCap이 nil이면 tx.GasTipCap()으로 폴백해 비교한다.
