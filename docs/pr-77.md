[StableNet] 거버넌스 GasTip 복원 제안 시 트랜잭션 Pending Pool 정체 이슈 수정



설명

Summary
거버넌스 GasTip 변경 이후, 빈 블록에서 currentBlock이 갱신되지 않는 문제 수정  

AnzeonTipEnv.SetCurrentBlock()가 state root 동일성만 체크하던 문제

RemotesBelowTip()에서 tx.GasTipCap()을 비교하던 로직을 수정하여, cached AnzeonTipCap이 있으면 해당 값을 우선 기준으로 판단하도록 변경

변경된 minTip 조건을 만족할 수 없는 트랜잭션이 remote pool에 남는 문제를 완화/수정

Background
1. AnzeonTipEnv: currentBlock 갱신 지연 문제
원인

블록 헤더의 GasTip은 부모 블록 state 기준으로 계산됨

따라서 block N에서 실행된 거버넌스 변경은 block N+1 header의 GasTip 값에 반영됨

문제 시나리오

block N+1이 빈 블록(empty block) 인 경우

state root가 block N과 동일

SetCurrentBlock()에서 갱신 조건(Root != header.Root)이 false → 업데이트 skip

영향

currentBlock이 여전히 block N 상태 유지 (변경 이전 GasTip)

GetAnzeonTipCap()이 stale 값 반환

결과적으로:

EffectiveGasTip < (업데이트된 minTip)

→ 해당 stale cache/minTip 조건에서는 블록 포함 대상에서 계속 제외됨

2. RemotesBelowTip: 잘못된 tip 비교 로직
원인

unauthorized account의 경우:

tx pool 검증 시 AnzeonTipEnv.GetAnzeonTipCap() 결과를 cache하며, unauthorized account는 block.GasTip()이 cache됨

→ 실제 실행 시 사용되는 effective tip

문제

RemotesBelowTip()이 tx.GasTipCap()만 기준으로 비교

영향

minTip이 증가한 경우:

GasTipCap ≥ threshold → 기존 RemotesBelowTip 기준에서는 drop 대상에서 제외 ✅

AnzeonTipCap < threshold → 실패 ❌

결과:

트랜잭션이 pool에서 제거되지 않음

동시에 블록에도 포함되지 않음

→ 최종 결과: pool에 stuck 상태의 dead transaction 발생

Changes
AnzeonTipEnv.SetCurrentBlock()

state root 비교 외에 GasTip 변경 여부(gasTipChanged()) 추가

→ 빈 블록에서도 currentBlock이 정상 갱신되도록 보장

RemotesBelowTip()

cached AnzeonTipCap이 있으면 해당 값으로 비교하고, cache가 없을 때만 tx.GasTipCap()으로 fallback

→ 실제 effective tip 기준으로 drop 여부 판단
